# Shared tutor feedback

Run [supabase_feedback.sql](./supabase_feedback.sql) in the SQL Editor of the same Supabase project configured in `src/utils/supabase.js`. This workspace has a public API key and cannot apply database migrations. The setup adds `tutor_ratings`, `tutor_comments`, and `tutor_comment_reactions` while preserving existing tutors and payments.

`testingfeedback` loads all records from the existing `public.tutors` table, ordered by `name` and `id`. Cards use `name`, `photoUrl`, `university`, and `verifiedStatus`, with subjects and bio displayed when present. Both the feedback drawer and **View all** use the original text tutor ID, such as `t10`. Unverified tutors are included. Pull down to refresh the list.

The highlighted star average and review count on the discovery **Tutor Profile** use a read-only `tutor_ratings` summary for the selected tutor. `TutorProfileRating` refreshes when the screen gains focus and displays a loading state or Retry if feedback cannot be read. An empty feedback table displays `0.0` and `0 reviews`; stored discovery averages are not used as a fallback. Other tutor fields and the booking flow retain their existing behavior. No discovery tables or hosted policies are written by the statistic.

The profile's **Reviews** card uses `TutorProfileReviews` to display the latest five top-level `tutor_comments` for the selected tutor, with the author's current rating from `tutor_ratings` matched by both tutor and user. Replies remain in **View all**, which opens the existing Feedback & Comments screen. Comments without a current rating display **Not rated**, and an empty comment list displays **No reviews yet**. The preview refreshes on screen focus and supports Retry after failed reads. It keeps the existing review card styling and reads public feedback without creating an auth session. The discovery `reviews` table is neither read nor written by this card; no database migration is needed for this preview if feedback is already configured.

On **Tutor Profile**, tapping the star average/review count or the **Reviews** card (including **No reviews yet**) opens the existing `TutorFeedbackDrawer` for that tutor and the current app user. From its summary, **Add a comment...** opens **Your feedback**, where users can rate and leave a comment using the same flow as `testingfeedback`. Closing the drawer reloads both profile feedback previews. **View all** still opens the full Feedback & Comments page; tapping it or Retry does not also open the drawer. Booking and favorite controls are independent of the feedback triggers.

**Recommended Tutors** and **search results** also display read-only `tutor_ratings` averages and counts. `useTutorRatingSummaries` fetches the list's feedback together in ID batches (up to 50 tutors per batch), follows every response page, and refreshes on screen focus. Cards preserve their existing compact/full-star layouts. Loading and unavailable feedback are distinguished from a genuine zero count. Search results load feedback for all fetched tutors before applying the existing filters and sorting. `withFeedbackRatings` overlays only the in-memory average/count fields, so rating thresholds, rating sorting, and recommended sorting use the same feedback shown on cards. The filter popup's preview count uses that same list. Failed rating reads show Retry rather than silently filtering against old scores. The existing filter rules and controls, Saved Tutors behavior, tutor details, prices, booking, compare, and favorite actions are unchanged; no database records are updated.

If feedback was installed with the earlier `profiles`/UUID schema, rerun the updated [supabase_feedback.sql](./supabase_feedback.sql) before using ratings or comments for these tutors. It changes feedback `tutor_id` columns to text and points new feedback at `public.tutors(id)`. Existing UUID-based feedback remains stored under its original ID; it is not reassigned to unrelated tutors. New foreign keys enforce valid tutors for new records while preserving those legacy records. The script does not edit tutors or payments. Tutor listing itself needs only read access to `public.tutors` for the app's anon/authenticated roles; the dashboard's `postgres` role does not prove app read access.

Screens live in `src/screens/`, reusable feedback views and the drawer in `src/components/`, Supabase operations in `src/services/feedback.js`, rating calculations in `src/data/feedback.js`, and the feedback hook in `src/hooks/useTutorFeedback.js`. SQL setup and documentation live beside the project's other Supabase setup files at the project root.

Normal signed-in accounts use their verified Supabase user ID. For the app's demo login, enable **Authentication → Sign In / Providers → Anonymous Sign-Ins** if it is not already enabled. Feedback reuses the app's existing anonymous demo identity; it creates that identity only when someone submits a rating, comment, or reaction. Shared feedback remains publicly readable.

Open **Payments → star → testingfeedback**, then tap a tutor. The drawer shows that tutor's rating average, rating distribution, and latest comment. Tapping **Add a comment...** opens the drawer's **Your feedback** form. Someone who has not rated this tutor must first select a star rating; the optional comment composer becomes available after the rating is saved. Existing ratings are shown automatically, allowing returning users to add a comment immediately or update their rating. **Done** returns to the summary without requiring a comment. Sending a comment also returns to the summary. **View all** opens **Feedback & Comments** with comment threads, replies, and like/dislike controls. Feedback is fetched again when the drawer opens or the full page's refresh button is pressed.

Every read filters by `tutor_id`. Ratings allow one entry per authenticated user per tutor, with subsequent selections updating that entry. Replies and reactions have composite foreign keys that prevent attaching them to another tutor's comments. RLS allows people to write ratings, comments, and reactions under their own Supabase user ID. Example names, comments, and review totals from the design references are not seeded into the database.

On **Feedback & Comments**, the three-dot menu appears on the current user's own comments and replies. **Edit** prefills the composer; the check button saves changes and the cancel control leaves the stored text intact. **Delete** opens a confirmation dialog. Deleting a parent comment also removes its replies and reactions; the confirmation explicitly explains this.

If feedback was already installed, rerun the updated [supabase_feedback.sql](./supabase_feedback.sql) to grant owner-only comment edit/delete permissions. Existing rows are preserved. Updates grant access only to the `body` column, so the author and tutor cannot be reassigned. The public key in this workspace cannot apply these hosted permission changes.

If the tables have not been created, the app displays an unavailable message and Retry. Failed writes retain the draft and show an error; successful writes are confirmed by Supabase before the composer clears.

Validation: Expo lint, TypeScript checking, web bundling, and isolated simulated Supabase checks. The migration and live database writes still require validation in the configured Supabase project.

Run comment mutation regression checks with `node --test tests/feedback-comments.test.js`.
